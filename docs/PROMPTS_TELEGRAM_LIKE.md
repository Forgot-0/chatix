# ChatiX → полноценный мессенджер: пакет промтов

Документ — не спецификация приложения, а **набор готовых промтов** для AI-агента
(Claude Code), которые последовательно превращают текущий ChatiX (рабочий, но
«дефолтно-материальный» клиент) в мессенджер уровня Telegram: со своей
айдентикой, своими фичами и полным использованием возможностей бэкенда из
[`api-docs.md`](../api-docs.md).

Принцип: **заимствуем проверенные паттерны взаимодействия, но не копируем
Telegram** — ни палитру, ни форму пузырей, ни иконки, ни тексты. Раздел 2
фиксирует, что берём, а что делаем своим.

---

## 1. Как этим пользоваться

1. **Один промт = одна сессия агента = один PR.** Не склеивать по два — контекст
   переполняется и качество падает.
2. Перед каждым промтом вставлять блок **«Общий контекст»** (§1.2). Он
   короткий и экономит агенту 10 минут разведки.
3. Порядок фаз важен: Фаза 0 задаёт дизайн-систему, на которую опираются все
   последующие экраны. Внутри фазы промты можно менять местами.
4. После каждого промта прогнать:

```bash
dart run build_runner build --delete-conflicting-outputs && flutter analyze && flutter test
```

5. Промты, помеченные 🔴, **требуют доработок бэкенда** — см. §4. Их можно
   выполнять в «локальном» режиме (состояние живёт только на устройстве), но
   об ограничении надо честно писать в UI и в PR.

### 1.2 Общий контекст (вставлять в начало каждого промта)

```text
Проект: Flutter-клиент мессенджера ChatiX (директория проекта — корень репозитория).
Бэкенд полностью описан в ./api-docs.md — это единственный источник правды по API,
читай нужные разделы перед работой, не выдумывай эндпоинты.

Архитектура (соблюдать строго, она уже выстроена):
- Clean Architecture: lib/features/<feature>/{domain,data,presentation}.
  domain — entities + repositories (абстракции) + usecases; data — models (json_serializable)
  + datasources + repositories impl; presentation — providers (Riverpod) + screens + widgets.
- Riverpod 3 (flutter_riverpod + riverpod_annotation), состояние — Notifier/AsyncNotifier.
- Ошибки — fpdart Either<Failure, T> в domain/data. UI разбирает Failure, а не исключения.
- Роутинг — go_router, все маршруты объявлены в lib/core/router/app_routes.dart,
  собраны в lib/core/router/app_router.dart. Новый экран = новый типизированный Route-класс там же.
- Сеть — dio, lib/core/network/api_client.dart + интерцепторы (auth/refresh, trailing slash, retry).
- Реалтайм — lib/core/websocket/chat_socket_service.dart (реконнект, heartbeat, resume,
  дедупликация по event_id уже реализованы — не переписывать, только расширять).
- Общие UI-примитивы — lib/core/ui/**. Новые переиспользуемые виджеты класть туда,
  специфичные для чата — в lib/features/chat/presentation/widgets/.
- Локализация — flutter gen_l10n: ARB лежат в lib/l10n/arb/intl_<locale>.arb (шаблон — intl_en.arb),
  генерация в lib/gen/l10n, настройки в l10n.yaml. ЛЮБАЯ новая пользовательская строка идёт в ARB,
  хардкод текста в виджетах запрещён.
- Линт строгий (analysis_options.yaml): prefer_single_quotes, always_declare_return_types и т.д.

Критичные особенности API (api-docs.md §0), нарушение = молчаливые баги:
- ВСЕ пути заканчиваются слэшем (redirect_slashes=False), иначе 404.
- Ошибки читаются как body['error']['code'], КРОМЕ 429 → body['detail'].
- Access-токен живёт 5 минут — полагаться на refresh-интерцептор, не кэшировать токен вручную.
- Пагинация двух видов: PageResult (has_next считать самому) и курсорная в чатах
  (has_next — реальное поле). Курсор списка чатов ДВУСОСТАВНОЙ: last_activity_at + last_chat_id.
- WS доставка at-least-once, дедуп по payload.event_id. Полный MessageDTO приходит
  только в new_message/message_edited; остальным событиям хватает дельты payload.event.
- Загрузка файлов — presigned PUT сырыми байтами (без multipart). Вложения чата: TTL 3600 с,
  подтверждение через .../confirm/, готовность — по WS-событию attachment_success.
- Ссылки на вложения (AttachmentDTO.url) живут 300 секунд — кэшировать файл по s3_key, НЕ url.

Definition of Done для любого промта:
- flutter analyze — ноль ошибок и ноль новых warning'ов;
- flutter test — зелёный; на новую логику (не на верстку) добавлены тесты;
- все новые строки — в ARB-файлах;
- светлая и тёмная тема выглядят одинаково законченно;
- никаких TODO-заглушек в пользовательских путях: либо фича работает, либо её нет в UI;
- в конце — краткий отчёт: что сделано, что осталось, какие места требуют бэкенда.
```

## 2. Дизайн-ориентир: «как Telegram, но своё»

### 2.1 Что заимствуем — паттерны, а не оформление

Это индустриальные паттерны мессенджеров, они не являются ничьей
собственностью и пользователь их ожидает:

- свайп по сообщению → ответ; долгое нажатие → контекстное меню действий;
- панель реакций поверх сообщения, «чипсы» реакций под ним;
- группировка подряд идущих сообщений одного автора, «хвост» только у последнего;
- липкий разделитель дат, разделитель «непрочитанные», плавающая кнопка
  «вниз» со счётчиком;
- цитата-ответ внутри пузыря с переходом к оригиналу;
- удержание кнопки микрофона для записи, свайп-отмена, свайп-вверх для
  фиксации записи;
- редактирование сообщения в том же поле ввода с баннером-контекстом;
- бесконечная лента вверх с курсорной подгрузкой.

### 2.2 Что делаем своим — айдентика ChatiX

Никакого «телеграм-синего», никаких треугольных хвостиков, никаких
скопированных иконок и микрокопии.

| Слой | Решение ChatiX |
|---|---|
| Палитра | Базовый акцент — **violet `#6E56F8`**, вторичный — **mint `#22C7A9`**, нейтрали тёплые (графит, не сине-серый). Семантика: успех — mint, опасность — coral `#F2624F`, внимание — amber `#F5A524`. |
| Пузыри | Исходящее — вертикальный градиент violet→indigo, текст белый. Входящее — surface + 1px hairline в светлой теме, приподнятая заливка в тёмной. Радиусы асимметричные: 20/20/20/6, «якорный угол» вместо хвостика. |
| Типографика | Переменный гротеск (Manrope или Inter Variable), **табличные цифры** для времени и счётчиков, чтобы не «прыгали». |
| Плотность | Три режима (компактный / обычный / просторный) — настраивается пользователем, не хардкод. |
| Обои чата | Не картинки, а **процедурные mesh-градиенты**, выведенные из акцента темы + опциональный паттерн-оверлей. Своя фича, генерится на клиенте, весит ноль байт. |
| Движение | Одна пружина на всё приложение (`Curves.easeOutCubic`, 220 мс базово; spring для жестов). Отправка — «взлёт и посадка», реакция — «расцветание», переходы экранов — shared-axis. |
| Цвет автора | Детерминированный оттенок из `user_id` — 8 палитр-акцентов, читаемых на обеих темах. |
| Микрокопия | Свой голос: короткий, без восклицаний, без «Ой!». Тексты пишутся сразу в ARB. |

#### П-5. 🔴 Умные папки, закрепление, архив

```text
[Общий контекст]
🔴 Бэкенд не хранит папки/закрепления/архив — всё локально на устройстве
(SharedPreferences/Hive). В UI это допустимо, но в PR явно указать, что состояние
не синхронизируется между устройствами, и оформить задачу на бэкенд (см. docs/BACKEND_GAPS.md).

Задача: дать пользователю управление списком чатов.

1. Закрепление чатов наверху (лимит 5), отдельная визуальная зона со своим фоном.
2. Архив: скрытая секция, доступная свайпом сверху списка или отдельной строкой-заголовком;
   архивированный чат возвращается в список при новом сообщении, если так настроено.
3. Умные папки — своя фича, не копия телеграмных папок. Папка = набор ПРАВИЛ, а не ручной список:
   - готовые: «Непрочитанные», «Личные», «Группы», «Каналы», «Без ответа от меня»;
   - пользовательские: конструктор правил (тип чата ∈ ..., есть непрочитанное,
```

## 4. Чего нет в бэкенде

Эти вещи нельзя сделать «правильно» на клиенте — их надо либо реализовать локально
с честной оговоркой, либо заводить задачу на бэкенд. Рекомендую при первом же прогоне
попросить агента создать `docs/BACKEND_GAPS.md` с этим списком и предлагаемыми контрактами.

| Возможность | Статус в API | Что делать сейчас |
|---|---|---|
| Индикатор «печатает» | `typing_start`/`typing_stop` объявлены в `WSEventType`, но никогда не публикуются (§6.4) | Виджет сделать, поток оставить пустым. Нужна публикация события + клиентская команда. |
| Закреплённые сообщения | Право `message:pin` есть в матрице ролей (§8.1), эндпоинта нет | Локальные «закладки» либо ничего. Нужен `POST/DELETE /chats/{id}/messages/{id}/pin/` + поле в `ChatDTO`. |
| Поиск по сообщениям | Эндпоинта нет | Поиск по локальному кэшу с явной плашкой. Нужен `GET /chats/{id}/messages/search/?q=`. |
| Онлайн/«был(а) в сети» | Только `is_online` в списке участников (`include_presence=true`) | Показывать онлайн там, где есть. Нужен `last_seen_at` и presence-события в WS. |
| Аватар чата | `ChatDTO.avatar_s3_key` только читается | Кнопки не добавлять. Нужен presign-флоу как у аватара профиля. |
| Отключение уведомлений по чату | Нет (`is_muted` — это модераторский мьют) | Локальная настройка. Нужно серверное поле, иначе не синхронизируется между устройствами. |
| Архив / закрепление / папки | Нет | Локально (П-5). Нужны серверные поля, чтобы переживать переустановку. |
| Черновики | Нет | Локально. |
| Входящий звонок | `call_*` события не публикуются, эндпоинта «завершить» нет (§5.6) | Только «присоединиться к звонку». Нужны call-события + push. |
| Удалить у себя / у всех | Только мягкое удаление для всех (§5.4) | Показывать одно действие «Удалить», без выбора. |
| История правок | Не хранится (§5.4) | Показывать только метку «изменено». |
| Стикеры, GIF, опросы | Нет | Не обещать в UI. |
| Общие медиа чата | Нет отдельного эндпоинта | Собирать из локального кэша. |
| Дедупликация direct-чатов | `DIRECT_CHAT_EXISTS` фактически не срабатывает (§5.2) | Проверять существующий direct-чат на клиенте ДО создания, иначе появятся дубли. |
| Передача владения чатом | Нельзя выдать роль `owner`, `created_by` не меняется (§5.2, §5.3) | Создатель не может покинуть чат — учесть в UI (П-16). |
